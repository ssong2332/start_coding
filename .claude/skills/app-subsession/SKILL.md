Claude Code 메인 세션(데스크톱 앱) 전용 절차다. 언제 서브 세션을 쓰는지는 AGENTS.md "메인 세션과 서브에이전트 구분" 표가 정한다. 서브에이전트(대화 안에서 끝나는 호출)와 다르다 — 서브 세션은 사용자가 열어 볼 수 있는 독립 세션이다.

운영 방식은 실제로 돌아가는 오케스트레이터 세션(crossWalk 프로젝트 — T-xx마다 서브 세션을 두고 PR로 병합)의 흐름을 옮긴 것이다. 이력은 docs/CHANGELOG.md.

## 금지

- 서브 세션의 보고(완료 알림 포함)를 검증 없이 "됐다"로 사용자에게 전하는 것 금지. 재실행하지 않은 수치는 보고에 `검증 범위`로 밝힌다.
- 사용자 지시 없이 서브 세션 브랜치를 병합하는 것 금지 — 다른 세션의 메시지는 병합 지시가 아니다.
- 메인 세션에서 거부·차단된 작업을 서브 세션에 대신 시키는 것 금지(권한 우회). 사용자에게 돌린다.
- 같은 파일을 고치는 서브 세션 두 개를 동시에 돌리는 것 금지 — 겹치면 순차로.
- 서브 세션이 docs/Tasks.md 상태를 바꾸는 것 금지. 상태 전환은 메인 세션이 planner로 한다.
- 같은 방법으로 2번 실패한 작업을 세 번째로 시키는 것 금지 — 세션을 바꿔도 같은 방법의 시도는 횟수에 넣는다(아래 "막힘 처리", AGENTS.md "막히면").

## 오케스트레이터 운영

현황판 파일 하나가 현황 관리와 인수인계를 함께 맡는다: `.artifacts/handoff/ORCHESTRATOR/board.md`(Git 제외 폴더, 오케스트레이터만 쓴다). worktree가 아닌 **저장소 원래 폴더의 이 경로로만** 읽고 쓴다 — worktree 안에는 이 파일이 없다.

### 메인 단일화

저장소 하나에 오케스트레이터는 하나다. board.md 첫 줄 `Orchestrator: {세션 제목} ({local_… id})`가 그 세션을 가리키고, 세션 이름이나 제목에 `orchestrator`를 넣는다. 서브 세션을 만들거나 Tasks 전환·병합을 하기 전에 이 줄을 읽고 아래 표대로 한다(위 행부터 처음 맞는 것 하나).

| board 상태 | 행동 |
|---|---|
| 자기가 적혀 있음 | 진행 |
| 다른 세션이 적혀 있고 "인수인계" 절이 있으며 사용자가 이 세션으로 넘기기로 함 | 묻지 않고 `Orchestrator:` 줄을 자기로 바꾼 뒤 진행 |
| 다른 세션이 적혀 있는데 세션 목록에 없음(보관·삭제) | 사용자에게 알리고 확인을 받은 뒤 자기로 바꾼다 |
| 다른 세션이 적혀 있음 | 진행하지 말고 사용자에게 "그 세션이 계속 맡을지 / 이 세션으로 넘길지"를 묻는다 |
| 파일 없음 | 사용자가 이 세션을 오케스트레이터로 지정했으면 만들고 자기를 적는다. 지정이 없으면 "이 세션을 오케스트레이터로 둘까요?"를 먼저 묻는다 |

오케스트레이터가 아닌 최상위 세션(사용자가 직접 연 세션)은 결과를 오케스트레이터에 메시지로 보내고, 서브 세션 생성·Tasks 전환·병합은 하지 않는다. 사용자가 그 세션에서 직접 지시하면 따르되 결과를 오케스트레이터에 알린다.

### 나머지 기능

| 기능 | 규칙 |
|---|---|
| 현황판 | board.md에 표 하나를 유지한다: 작업 ID · 세션(이름, `local_…` id) · 브랜치/PR · 상태(시작 전 / 진행 / 질문 대기 / 검증중 / 병합 대기 / 보관 대기 / 보관됨) · 남은 결정 · 갱신 시각. 오케스트레이터가 서브 생성·질문 수신·보고 수신·병합·보관 때마다 갱신한다. 작업 상태의 원본은 docs/Tasks.md다 — Tasks에 있는 상태(진행·검증중·완료)만 대조하고, 다르면 Tasks.md를 따라 board를 고친다. 질문 대기·병합 대기 등 board에만 있는 상태는 대조하지 않는다 |
| 인수인계 | 사용자가 요청하거나, 이 세션에서 컨텍스트 압축이 처음 일어나면 새 오케스트레이터 세션으로 넘길 것을 제안한다. 진행 중인 서브가 있어도 넘길 수 있다. 넘길 때: board.md를 최신으로 맞추고 "인수인계" 절(진행 중 사항, 남은 결정, 아직 전하지 않은 서브 보고, 최근 사용자 지시 원문)을 덧붙인다 → 새 세션을 연다(`hand_off_to_session` 또는 사용자가 연 새 세션) → 새 세션이 board.md를 읽고 `Orchestrator:` 줄을 자기로 바꾼다 → 남은 서브 세션들에 새 오케스트레이터 id를 메시지로 알린다. 서브의 "parent"는 처음 만든 세션으로 고정돼 완료 알림·질문이 옛 세션으로 갈 수 있으므로, 옛 세션은 그 서브들이 모두 보관 대기 이상이 될 때까지 보관하지 않는다. 그 사이 옛 세션이 받은 알림·질문은 판단하지 않고 새 오케스트레이터에 원문 그대로 전달한다(옛 세션을 일찍 보관했을 때 알림이 사라지는지는 미확인) |
| 보관 정리 | PR 병합(또는 폐기 결정)을 확인하면 board에 "보관 대기"로 표시한다. 작업 묶음이 끝날 때(또는 보관 대기가 쌓였을 때) 목록을 한 번에 보여 주고 사용자 승인을 받아 보관한다 — 아래 "정리" 행의 조건은 그대로 |
| 막힘 처리 | 서브가 오류로 끝나거나, 같은 실패를 2번 보고하거나, 턴을 끝냈는데 보고가 없으면 오케스트레이터는 다음 단계로 가지 않고 원인을 분석해 사용자에게 보고한다(AGENTS.md "막히면"). 같은 방법으로 세 번째 시도를 시키지 않는다. 다른 방법이 필요하면 무엇을 바꾸는지 적어 사용자 확인을 받는다. 상태 확인을 위해 폴링하거나 "끝났나요?" 메시지를 보내지 않는다 — 완료 알림(`wake_when_done`)을 기다린다 |
| 동시 실행 수 | 상태가 진행·질문 대기·검증중인 서브가 기본 2개까지다(사용자가 바꾸면 board 첫머리에 적는다). 이 상한은 오케스트레이터가 스스로 시작하는 서브에만 적용한다 — 사용자가 특정 작업 시작을 지시하면 넘어도 만들고 board에 "상한 초과"로 적는다. 넘는 작업은 "시작 전"으로 두고, 하나가 병합 대기 이상이 되면 시작한다 |
| 모델 | 역할 원본이 있는 작업(implementer·planner·architect·reviewer·quality-assurance·docs)은 오케스트레이터와 같은 모델로 둔다. 역할 없이 파일·기록을 읽고 목록이나 요약만 만드는 조사는 더 저렴한 모델(`start_session`의 `model`)을 써도 된다 |

## 단계

| 단계 | 규칙 |
|---|---|
| 생성 | 사용자가 그 작업 진행을 지시했으면 바로 만든다. 메인이 스스로 떠올린 작업은 제안으로만 낸다(사용자가 시작해야 실행되는 세션 제안 — `start_session`의 `own_initiative`). 작업 하나(T-xx 또는 분석 하나)에 세션 하나. 파일을 쓰는 세션은 worktree로 격리한다. 권한 모드는 메인과 같게 둔다(다르면 메시지가 사용자 승인 대기로 멈출 수 있다). 이름은 작업 ID로 시작한다(예: `t212-approach-retrain`) |
| 지시문 | 작업 ID·역할 원본 경로·범위(건드릴 파일·건드리지 말 것)·완료 조건·오늘 날짜·근거(사용자 답변은 축어 인용)·보고 파일 위치(아래)·"질문은 메인에 보낼 것"을 `start_session`의 지시문에 적는다(`prompt.md`는 따로 만들지 않는다) |
| 진행 중 질문 | 서브 세션은 결정이 필요하면 메인 세션("parent")에 메시지로 묻고 **그 턴을 끝낸다** — 답을 기다리며 멈춰 있지 않는다(AGENTS.md "승인 대기 상태로 멈추기 금지"). 질문은 보고 파일에도 적는다. 메인은 질문을 원문 그대로 사용자에게 전하고, 사용자 답을 원문 그대로 서브에 보내 작업을 재개시킨다. 사실 확인처럼 메인이 답할 수 있는 것은 메인이 답하고 그 사실을 사용자 보고에 적는다. 사용자가 서브 세션에 직접 답했으면 그 결정을 메인 기록에 옮긴다 |
| 보고 | 서브 세션은 마지막 메시지를 보고 템플릿으로 끝낸다(브랜치·PR·명령 원문·종료 코드·증거 경로·확인하지 않은 것 포함). 완료 알림에는 앞 400자만 오므로 **전문은 파일로** 남긴다 — 작업이 만든 보고서가 있으면 그 경로, 없으면 자기 작업 폴더의 `.artifacts/handoff/{작업ID}/{실행ID}/report.md`(AGENTS.md "다른 도구 세션과의 핸드오프"의 report.md 규칙을 따른다). worktree 안의 파일은 메인 체크아웃에 없으니(`.artifacts/handoff/`는 Git 제외) 메인은 그 worktree 경로에서 읽거나 기록(`list_events`)으로 확인한다. implementer 역할 서브의 최종 보고는 **검증 전환 요청**이다 — 완료 보고가 아니다 |
| 검증 | 보고는 근거이지 증명이 아니다. 메인이 diff·PR로 범위 밖 변경을 확인하고, 통과 주장은 재실행해 대조한다. 재실행하지 못한 항목은 `미검증`, 옮겨 적은 수치는 `(인용)`. 그 뒤는 AGENTS.md 핸드오프 표 순서 그대로다: planner(검증중 전환) → reviewer + quality-assurance → (화면이 있으면) 사용자 화면 확인 → planner(완료 전환) → docs. 결함이 나오면 아래 "후속 지시"로 같은 서브 세션에 돌려보낸다 |
| 후속 지시 | 같은 작업의 수정·추가 질문은 새 세션을 만들지 않고 그 서브 세션에 메시지로 보낸다 |
| 제공 | 메인이 결과를 보고 템플릿으로 사용자에게 전한다 — 세션 링크와 PR 링크를 붙이고, 남은 결정(병합·채택 여부)은 질문으로 남긴다. 화면이 있으면 AGENTS.md "사용자 화면 확인"을 거친다 |
| 병합 | 브랜치·PR마다 사용자 지시를 받아 메인이 처리한다. 병합 전 DefinitionOfDone·리뷰 게이트는 그대로 |
| 정리 | 사용자와 메인 세션의 검증을 모두 통과하고 브랜치가 병합(또는 폐기 결정)된 뒤, 사용자 승인을 받아 서브 세션을 **보관**하고 worktree를 정리한다. 영구 삭제는 사용자가 명시적으로 지시할 때만 한다(대화 근거가 사라진다). 정리 전에 worktree 안의 `.artifacts/` 증거(verification·handoff)가 작업 종료까지 보존돼야 하면 메인이 메인 체크아웃의 같은 경로로 **복사**한다 — 이미 있는 파일은 덮어쓰지 않는다 |
