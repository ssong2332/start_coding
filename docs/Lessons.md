# 교훈 기록 — {{PROJECT_NAME}}

> 소유자: 사용자 | 행 추가는 메인 세션만 (append-only). 이 프로젝트에서 검증된 작업이 바로잡은 **틀린 가정**과 **안 통한 시도**를 남겨, 다음 작업이 같은 조사를 반복하지 않게 한다.

## 금지

- 해결·검증되지 않은 문제를 적는 것 금지. 재현 테스트 통과나 실측 근거가 있어야 한다.
- 계획대로 끝난 작업을 적는 것 금지 — 작업량·diff 크기는 자격이 아니다.
- 현재 코드·테스트·CodingRules·DECISIONS·ADR에서 이미 읽어낼 수 있는 내용을 다시 적는 것 금지.
- 과거 행의 내용을 고치거나 지우는 것 금지 (상태 열만 갱신).
- 시크릿·개인정보·외부 로그 원문을 적는 것 금지.
- 킷 규칙·훅·스크립트 때문에 막힌 일을 여기 적는 것 금지 — 그건 docs/KitFeedback.md.
- 예시 행을 미리 채워 두는 것 금지 (실제 교훈으로 오인된다 — docs/UpdateRequests.md와 같은 이유).

## 적을 자격 (전부 '예'여야 한다)

| 질문 | '아니오'면 |
|---|---|
| 문제가 해결됐고 그 근거(테스트 출력·실측)가 있는가? | 적지 않는다 |
| 이 기록이 없으면, 현재 저장소만 보고 일하는 다음 작업자가 같은 실수를 하거나 같은 조사를 다시 할 가능성이 높은가? | 적지 않는다 |
| 아래 "형태 고르기"의 1·2번으로는 담을 수 없는 내용이 남는가? | 1·2번만 처리하고 행은 추가하지 않는다 |

## 형태 고르기 (위에서부터 처음 맞는 것)

| 순서 | 형태 | 맞는 경우 | 누가 |
|---|---|---|---|
| 1 | 검사 (재현 테스트) | 테스트가 같은 결함을 기계적으로 잡을 수 있다 | implementer — `.agents/skills/tdd-practitioner/SKILL.md` 버그 수정 절차. 이미 있으면 추가 작업 없음 |
| 2 | 규칙 한 줄 | 작성 중에 피해야 하고 리뷰어가 diff에서 볼 수 있으나 테스트로는 못 잡는다 | 메인 세션이 "CodingRules 추가 권고"로 사용자에게 보고 (직접 수정하지 않는다) |
| 3 | 이 문서의 행 | 코드·테스트·규칙이 담지 못하는 이유·측정값·기각된 대안 | 메인 세션 |

1·2번을 처리한 뒤 자격 질문을 한 번 더 한다. 더 잃을 것이 없으면 행을 추가하지 않는다.

## 교훈 목록

| # | 날짜 | 작업 ID | 영역 (모듈·기능) | 틀렸던 가정 또는 증상 | 시도했지만 안 통한 것 (이유) | 실제 원인과 통한 해결 | 재발 방지 (형태 + 위치) | 폐기 조건 | 상태 |
|---|---|---|---|---|---|---|---|---|---|

행이 비어 있으면 지금까지 자격을 통과한 교훈이 없다는 뜻이다.

상태값: `유효` / `폐기 — {사유, 날짜}`. 폐기 조건은 "이 교훈이 더는 참이 아니게 되는 외부 변화와 확인 방법"을 적는다. 없으면 `해당 없음 — {사유}`.

## 쓰는 절차 (메인 세션)

1. 서브에이전트 보고의 "문제/다음 단계"에 `교훈 후보:`가 있거나, 메인 세션이 직접 겪은 경우에만 시작한다.
2. "적을 자격" 표를 적용한다. 통과하지 못하면 아무것도 쓰지 않고 그 사실을 보고에 한 줄 적는다.
3. 한 번에 교훈 하나. 같은 영역에 `유효`인 행이 이미 같은 내용을 담고 있으면 새 행을 만들지 않는다.
4. 사용자에게 먼저 묻지 않고 행을 추가하며, 최종 보고에 추가한 행 번호를 적는다 (AGENTS.md 문서 소유권 표가 메인 세션의 행 추가를 허용한다).

## 읽는 절차

planner·architect·implementer·reviewer는 작업 전에 이 문서에서 **이번 작업과 영역이 겹치는 `유효` 행**을 읽는다. 행의 내용이 현재 코드와 어긋나면 그대로 따르지 말고 보고에 `교훈 #n 낡음 의심`으로 적는다 — 상태 전환은 메인 세션이 사용자 확인 후 한다.
